> **所属项目**：MES Lite — 轻量级离散制造执行系统
> **优化范围**：工单看板列表与详情、设备状态上报与看板、批次追溯查询、报工与审计写入、OEE 聚合
> **创建时间**：2026-03-19
> **设计角色**：Performance Engineer
> **上游依赖**：`docs/01-需求规格书.md`（NFR-001 ~ NFR-003 指标口径）、`docs/04-详细设计说明书.md`（索引、缓存、事务与并发设计）、`docs/07-接口数据契约.md`（端点与分页约定）
> **演示说明**：本文档是 MES Lite 通用离散制造演示交付的一部分；环境、地址、压测数据与实测值均为通用演示数据，不对应任何真实生产环境。

### 2.3 测试脚本示例（k6）

```javascript
// perf/perf-001-work-order-list.js
import http from 'k6/http';
import { check, sleep } from 'k6';

export const options = {
  stages: [
    { duration: '2m', target: 50 },
    { duration: '5m', target: 200 },
    { duration: '5m', target: 500 },
    { duration: '2m', target: 0 },
  ],
  thresholds: {
    http_req_duration: ['p(95)<500', 'p(99)<1500'],
    http_req_failed: ['rate<0.001'],
  },
};

const BASE = 'http://localhost:8080';
const TOKEN = __ENV.MES_TOKEN;

export default function () {
  const url = BASE
    + '/api/work-orders?page=1&size=20&status=SCHEDULED,IN_PROGRESS&sort=plannedStartTime,asc';
  const headers = {
    Authorization: 'Bearer ' + TOKEN,
    'X-Trace-Id': 'k6-' + __VU + '-' + __ITER,
  };
  const res = http.get(url, { headers: headers });
  check(res, {
    'status is 200': (r) => r.status === 200,
    'code is OK': (r) => r.json('code') === 'OK',
    'list is array': (r) => Array.isArray(r.json('data.list')),
  });
  sleep(1);
}
```

设备上报场景（PERF-004）使用 `constant-arrival-rate` 执行器，按 200 台设备每 5s 一次计算速率，并在脚本内轮换 200 个设备编码，其中 5s 窗口内的重复上报占 10%，用于验证幂等短路路径的耗时。

## 3. 性能瓶颈分析

### 3.1 瓶颈清单

| 瓶颈编号 | 瓶颈描述 | 层级 | 现象 | 根因 | 严重级别 | 影响范围 |
| --- | --- | --- | --- | --- | --- | --- |
| BOT-001 | 工单看板列表查询慢 | 数据库 | 50 万行下 P95 980ms，深分页 P99 3.2s | 缺少 `(status, planned_start_time)` 覆盖索引；`count(*)` 全表聚合 | 🔴 高 | 全部角色 |
| BOT-002 | 工单详情 N+1 查询 | 应用层 | 单请求 42 条 SQL，详情 P95 760ms | 工序、报工、投料、检验按行循环查询 | 🔴 高 | 工单详情页 |
| BOT-003 | 设备看板每次实时聚合 | 数据库 / 应用层 | 200 台设备时 P95 640ms，DB CPU 峰值 70% | 每次请求用窗口函数取每台设备最新状态，扫描状态历史大表 | 🔴 高 | 设备看板（10s 轮询） |
| BOT-004 | 追溯递归查询全表扫描 | 数据库 | 3 层链路 P95 6.8s，超 NFR-003 | `batch_feeding` 缺少反向索引，递归 CTE 每层顺序扫描 | 🔴 高 | 追溯查询 |
| BOT-005 | 报工写入被审计同步写拖慢 | 应用层 | 写入 P95 1.35s，超 NFR-001 的 800ms | 审计日志与业务在同一事务内同步写入，且逐条提交 | 🟡 中 | 报工、投料、判定 |
| BOT-006 | OEE 日聚合重复扫描 | 数据库 | 单设备单日聚合 1.4s，看板联动查询超时 | 每次查询实时扫描 2 万条状态记录并现算停机时长 | 🟡 中 | OEE 面板 |
| BOT-007 | 连接池等待 | 应用层 | 500 VU 时 `hikaricp_connections_pending` 峰值 12 | `maximumPoolSize = 10`（初始配置）偏小；只读事务未分离 | 🟡 中 | 全部接口 |

### 3.2 瓶颈详情

#### BOT-001：工单看板列表查询慢

- **SQL**：`SELECT ... FROM work_order WHERE is_deleted = 0 AND status IN (...) ORDER BY planned_start_time ASC LIMIT 20 OFFSET 20000`
- **EXPLAIN 结果（优化前）**：`Seq Scan on work_order (rows=500000)`，`Sort Method: external merge Disk: 45MB`；深分页 `OFFSET 20000` 需回表过滤 2 万行。
- **CPU 使用率**：数据库 CPU 峰值 88%，该查询占 62%。
- **建议索引**：`CREATE INDEX CONCURRENTLY idx_wo_status_plan_start ON work_order(status, planned_start_time DESC) WHERE is_deleted = 0;`
- **补充措施**：`total` 超过 10 万行时返回估算值（`totalIsEstimate = true`），避免每次都做精确 `count(*)`。

#### BOT-002：工单详情 N+1 查询

- **现象**：单请求 SQL 条数 42；`work_order_operation` 2 条、`work_order_report` 12 条、`batch_feeding` 17 条、`inspection_order` 11 条。
- **根因**：详情装配按集合逐元素查询，未做 IN 批量合并。
- **定位手段**：p6spy 按 `traceId` 聚合每请求 SQL 条数；阈值告警设为 > 10 条。

#### BOT-004：追溯递归查询全表扫描

- **SQL**：`WITH RECURSIVE chain AS (SELECT ... FROM batch_feeding WHERE work_order_id = ? UNION ALL SELECT ... FROM batch_feeding bf JOIN chain c ON bf.work_order_id = ...)`
- **EXPLAIN 结果（优化前）**：每层 `Seq Scan on batch_feeding (rows=1000000)`，3 层累计扫描 300 万行。
- **建议索引**：`idx_bf_batch (material_batch_no, work_order_id)` 与 `idx_bf_wo (work_order_id)`；同时把结果集上限与深度上限下推到 SQL。
- **附加裁剪**：`LIMIT 1000` 在递归外层生效，超出时返回 `truncated = true`。

## 4. 缓存策略设计

### 4.1 缓存层级架构

```text
┌──────────────────────────┐
│ 浏览器缓存                │ ← 静态资源 Cache-Control、看板本地节流
├──────────────────────────┤
│ 应用进程内 Caffeine (L1)  │ ← 字典、设备台账、工作中心、看板快照
├──────────────────────────┤
│ Redis (L2)               │ ← 看板快照、工单详情热点、追溯结果、防重复提交
├──────────────────────────┤
│ PostgreSQL (源)          │ ← 权威数据；缓存未命中或降级时回源
└──────────────────────────┘
```

### 4.2 各层缓存配置

| 缓存层 | 数据类型 | TTL | 最大容量 | 淘汰策略 | 失效方式 |
| --- | --- | --- | --- | --- | --- |
| Caffeine | 字典（报废原因、停机原因、单位） | 10min | 500 条 | LRU | 定时刷新 + 管理端手动失效 |
| Caffeine | 设备台账、工作中心、班次日历 | 5min | 500 条 | LRU | 台账或日历变更时主动失效 |
| Caffeine | 设备看板快照 | 5s | 1 份 | 覆盖写 | 定时任务覆盖 + 状态变更延迟双删 |
| Redis | 设备看板快照键 `meslite:board:v1` | 5s | 约 20KB | 覆盖写 | 状态变更后延迟 500ms 二次删除 |
| Redis | 工单详情热点（当日活跃工单） | 60s | 2 万键 | allkeys-lru | 报工 / 状态变更时删除对应键 |
| Redis | 追溯查询结果 | 60s | 5000 键 | allkeys-lru | 键含锚点与方向；投料或处置变更时按锚点删除 |
| Redis | 防重复提交令牌 | 30s | 1 万键 | allkeys-lru | 自然过期 |

明确不缓存的内容：工单列表分页结果（条件组合多、命中率低）、批次可用库存（BR-012 要求实时）、状态变更响应（幂等由 `version` 与唯一索引保证）。

### 4.3 缓存风险防护

| 风险类型 | 场景 | 防护策略 |
| --- | --- | --- |
| 缓存雪崩 | 大量键同时过期 | TTL 加 ±20% 随机偏移；看板快照由单一定时任务覆盖写，不参与批量过期 |
| 缓存击穿 | 看板快照键过期瞬间高并发回源 | 快照写入使用互斥锁 + 双检；回源期间返回上一次快照并置 `stale = true` |
| 缓存穿透 | 查询不存在的批次号或工单号 | 空结果短缓存 30s；接口层先做格式校验 |
| 数据一致性 | 看板显示过期状态导致现场误判 | 快照携带 `snapshotAt` 并由前端展示；状态变更后延迟双删；超 30s 未更新显示降级提示 |
| 降级 | Redis 不可用 | `CacheFallbackTemplate` 捕获异常后直接回源数据库，不阻断请求；看板置 `stale = true` |

## 5. 优化方案

### 5.1 优化项清单

| 优化编号 | 优化项 | 层级 | 方案 | 预期收益 | 风险 | 优先级 |
| --- | --- | --- | --- | --- | --- | --- |
| OPT-001 | 工单看板复合覆盖索引 | 数据库 | `CREATE INDEX CONCURRENTLY idx_wo_status_plan_start ON work_order(status, planned_start_time DESC) WHERE is_deleted = 0` | 列表 P95 980ms → 210ms | 写入索引维护开销约 +5% | P0 |
| OPT-002 | 消除工单详情 N+1 | 应用层 | 工序、报工、投料、检验改为 IN 批量装配并一次合并为 5 条查询 | 详情 P95 760ms → 180ms；SQL 42 → 6 条 | 单请求内存占用略升 | P0 |
| OPT-003 | 设备看板两级缓存 + 快照任务 | 缓存 | `BoardSnapshotJob` 每 5s 聚合写 Redis，L1 Caffeine TTL 5s；上报路径不再触发聚合 | 看板 P95 640ms → 45ms；DB CPU 70% → 22% | 最长 5s 状态延迟，需 UI 明示 | P0 |
| OPT-004 | 追溯双向索引 + 递归裁剪 | 数据库 / 应用层 | 建 `idx_bf_batch`、`idx_bf_wo`；递归 CTE 下推深度与 `LIMIT 1000` | 3 层 P95 6.8s → 1.6s | 超限结果被裁剪，需 `truncated` 标记 | P0 |
| OPT-005 | 审计异步写入 + 批量提交 | 应用层 | 审计切面投递本地队列，50 条或 200ms 触发批量插入；失败重试 3 次后同步降级 | 写入 P95 1.35s → 520ms | 审计存在秒级延迟，需对账 | P0 |
| OPT-006 | 设备状态历史年分区 + 幂等短路 | 数据库 | 按年范围分区；`report_key` 唯一索引前置短路，命中即返回不写库 | 上报单条 78ms → 21ms；历史查询 P95 420ms | 需提前创建次年分区 | P1 |
| OPT-007 | OEE 日粒度预聚合 | 数据库 | 新增 `oee_daily` 表，定时任务落库；查询不再扫描状态记录 | OEE 查询 1.4s → 60ms | 预聚合延迟（小时级） | P1 |
| OPT-008 | 连接池与只读事务调优 | 应用层 | `maximumPoolSize` 10 → 20，`minimumIdle` 5；只读查询显式 `readOnly = true` 走独立只读连接策略 | 池等待峰值 12 → 0；查询 P95 -8% | 连接数上升，需核对 DB `max_connections` | P1 |
| OPT-009 | 列表 `total` 估算保护 | 应用层 | 行数超过 10 万时以 `pg_class.reltuples` 估算并置 `totalIsEstimate` | 深分页 P99 3.2s → 0.6s | 总数不精确，需前端提示 | P1 |

### 5.2 OPT-001 详细方案

- **修改文件**：`src/main/resources/db/migration/V2__index_and_partition.sql`
- **SQL**：`CREATE INDEX CONCURRENTLY idx_wo_status_plan_start ON work_order (status, planned_start_time DESC) WHERE is_deleted = 0;`
- **上线方式**：`CREATE INDEX CONCURRENTLY` 在线创建，不锁表；执行期间监控 `pg_stat_progress_create_index`。
- **回滚方案**：`DROP INDEX CONCURRENTLY idx_wo_status_plan_start;`（无数据变更，回滚即时生效）
- **验证方式**：`EXPLAIN (ANALYZE, BUFFERS)` 确认走 `Index Scan using idx_wo_status_plan_start`，且 `Buffers: shared hit` 占比 > 95%；重跑 PERF-001 对比 P95。

### 5.3 OPT-005 详细方案

- **修改文件**：`meslite-security/src/main/java/.../AuditLogRecorder.java`、`AuditBatchWriter.java`
- **实现要点**：AOP 切面构造审计对象后投入有界队列（容量 20000），写入线程按「50 条或 200ms」批量提交；队列满时降级为同步写入并告警；写入失败按 1s / 5s / 30s 重试 3 次，仍失败置死信并告警。
- **一致性保障**：接口成功返回即视为「已受理审计」；审计写入失败率阈值 0.01%（NFR-006），超阈值告警并按日与业务写操作条数对账。
- **回滚方案**：配置开关 `meslite.audit.mode = sync` 一键回到同步写入，无需发布。

## 6. 性能优化前后对比

> ⚠️ 以下数据基于演示测试环境（4C8G 单实例 + PostgreSQL 16 单主库），压测时间 2026-03-19，数据量为 50 万工单 / 100 万投料记录 / 600 万设备状态记录。

| 指标 | 优化前 | 优化后 | 改善幅度 | 对应目标 |
| --- | --- | --- | --- | --- |
| 工单列表 P50 | 210ms | 62ms | ↓ 70% | P50 ≤ 150ms |
| 工单列表 P95 | 980ms | 210ms | ↓ 79% | NFR-001 P95 ≤ 500ms |
| 工单列表深分页 P99 | 3200ms | 640ms | ↓ 80% | NFR-001 P99 ≤ 1500ms |
| 工单详情 P95 | 760ms | 180ms | ↓ 76% | NFR-001 |
| 单请求 SQL 条数（详情） | 42 | 6 | ↓ 86% | 设计目标 ≤ 6 |
| 设备看板刷新 P95 | 640ms | 45ms | ↓ 93% | NFR-002 刷新 ≤ 10s |
| 设备单条上报处理 P95 | 78ms | 21ms | ↓ 73% | NFR-002 ≤ 200ms |
| 设备上报可达速率 | 60 次/秒（错误率升） | 210 次/秒 | ↑ 250% | NFR-002 峰值 120 次/秒 |
| 追溯 3 层链路 P95 | 6800ms | 1600ms | ↓ 76% | NFR-003 3 层 ≤ 5s |
| 追溯单层 P95 | 1900ms | 420ms | ↓ 78% | NFR-003 单层 ≤ 2s |
| 报工写入 P95 | 1350ms | 520ms | ↓ 61% | NFR-001 写入 P95 ≤ 800ms |
| OEE 日查询 P95 | 1400ms | 60ms | ↓ 96% | 派生数据目标 ≤ 500ms |
| 连接池待获取连接峰值 | 12 | 0 | ↓ 100% | 设计目标 ≤ 2 |
| 数据库 CPU 峰值 | 88% | 46% | ↓ 48% | 容量规划基线 |
| 看板缓存 L1 命中率 | — | 0.94 | — | 设计目标 ≥ 0.90 |
| 混合场景错误率 | 0.42% | 0.03% | ↓ 93% | AC-030 ≤ 0.1% |

结论：全部指标在演示数据集下满足 NFR-001 ~ NFR-003 与 AC-030；优化前不达标的 6 项（列表 P95 / 深分页 P99 / 设备看板 / 追溯 3 层 / 报工写入 / 错误率）均已达标，其余各项保留 ≥ 30% 余量。

## 7. 生产性能监控建议

### 7.1 关键指标（Golden Signals）

| 信号 | 指标 | 采集方式 |
| --- | --- | --- |
| 延迟 | `http_server_requests_seconds`（按 `uri` 分位）、`eq_report_duration_seconds`、`trace_query_duration_seconds` | Micrometer + Prometheus Histogram |
| 流量 | `http_server_requests_seconds_count`、`eq_report_total`、`wo_report_total` | Prometheus Counter |
| 错误率 | 5xx 占比、`wo_state_conflict_total`、`qc_blocked_total` | Prometheus Counter |
| 饱和度 | CPU / 内存、`hikaricp_connections_pending`、`outbox_pending_count`、`pg_stat_activity` 活跃连接 | Node Exporter、Micrometer、`pg_stat_statements` |
| 缓存 | `cache_get_hit_ratio{layer}`、Redis `keyspace_hits` / `keyspace_misses` | Micrometer + Redis INFO |
| 定时任务 | 快照写入间隔、离线判定耗时、OEE 聚合耗时、归档任务结果 | 任务执行日志 + 自定义 Timer |

### 7.2 告警阈值

| 告警规则 | 级别 | 阈值 | 处理建议 |
| --- | --- | --- | --- |
| 查询 P95 > 500ms | Warning | 持续 5min | 检查慢查询与索引命中率、缓存命中率 |
| 查询 P99 > 1500ms | Critical | 持续 2min | 考虑限流、收窄列表条件或扩容 |
| 写入 P95 > 800ms | Warning | 持续 5min | 检查锁等待、审计队列深度、`db_lock_timeout_total` |
| 单条上报 P95 > 200ms | Warning | 持续 10min | 检查分区裁剪、幂等短路命中率、网关重传比例 |
| 错误率 > 0.1% | Warning | 持续 5min | 排查下游依赖与慢 SQL（AC-030 阈值） |
| 错误率 > 1% | Critical | 持续 1min | 立即排查或回滚 |
| DB 连接池待获取 > 2 | Warning | 持续 10min | 检查连接泄漏、慢事务与池大小 |
| `outbox_pending_count` > 5000 | Warning | 持续 10min | 检查消费线程与失败重试，必要时手工补建检验单 |
| 审计写入失败率 > 0.01% | Critical | 持续 5min | 切换同步写入模式并告警（NFR-006） |
| 缓存 L1 命中率 < 0.90 | Warning | 持续 15min | 检查 TTL 与快照任务是否正常 |
| 次年分区缺失 | Critical | 立即 | 补建分区，否则设备状态插入将失败（ADR-004） |
| 数据库 CPU > 80% | Warning | 持续 10min | 评估只读副本或查询优化 |

## 8. 容量规划

| 指标 | 当前容量（演示环境） | 6 个月预估 | 12 个月预估 | 扩容触发条件 |
| --- | --- | --- | --- | --- |
| 应用 QPS（混合） | 实测可达 420（P95 达标 260） | 60 | 90 | 峰值 QPS > 达标容量 × 70% |
| 设备上报速率 | 实测可达 210 次/秒 | 40 次/秒（200 台 × 5s） | 40 次/秒（设备数不变） | 接入设备 > 200 台时启用批量上报端点 |
| 数据库存储 | 约 6.5 GB | 约 8.5 GB | 约 11 GB | 使用率 > 80%；`equipment_status_log` 与 `audit_log` 按年归档 |

## 10. 风险与假设

| 类别 | 内容 |
| --- | --- |
| 环境差异 | 测试环境为单实例且压测客户端同机，生产环境存在负载均衡与跨机网络；性能差距估计 ±20%，达标结论需在生产预发环境复验 |
| 数据量假设 | 基于 50 万工单 / 100 万投料 / 600 万设备状态记录的演示数据集；若设备接入超过 200 台或上报间隔缩短，需重新压测（OPT-006 的分区与幂等策略需复评） |
| 未覆盖场景 | 未压测 Excel 导入大文件（> 5000 行）与追溯报告大批量导出；未压测极端班次场景（交班 10 分钟内集中报工） |
| 缓存一致性 | 看板存在最长 5s 状态延迟，已通过 `snapshotAt` 与降级提示缓解，但现场对「实时性」的接受度需在试运行班次中确认 |
| 审计时延 | 审计异步写入带来秒级延迟；若合规要求「返回即落库」严格成立，需退回同步模式并重新评估写入 P95 目标 |
| 口径依赖 | OEE 分母是否含计划保养尚未与设备部门确认（设计 Q-03），口径变化会影响聚合耗时与 `oee_daily` 结构 |
| 索引维护开销 | OPT-001、OPT-004 的索引使报工与投料写入开销上升约 5%，已在第 6 节对比中计入；后续新增索引须复测写入 P95 |

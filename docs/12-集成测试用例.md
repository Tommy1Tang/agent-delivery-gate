### 用例设计规则

1. **分层穿透**：每条用例至少穿透 API、Service、Mapper 三层，禁止仅断言 Service 返回值；SQL 断言通过 `JdbcTemplate` 直查结果核对。
2. **事务边界**：凡涉及多表写入的用例必须给出「提交后可见」与「失败后整体回滚」两个方向的断言（IT-003、IT-027、IT-036、IT-038）。
3. **约束兜底**：应用层校验与数据库约束成对验证——先构造绕过应用层校验的直写语句，确认数据库约束仍然拒绝（IT-002、IT-013、IT-020、IT-042）。
4. **并发确定性**：竞态用例使用同步栅栏起跑并断言「恰好一个成功、另一个得到约定错误码」，不接受「多数成功」这类模糊断言。
5. **时延与计划**：性能相关用例先断言执行计划（`EXPLAIN (ANALYZE, BUFFERS)` 命中预期索引），再断言时延分位数。
6. **数据规模**：追溯与列表性能用例使用批量夹具注入真实数据量（5 万工单 / 100 万投料记录），不使用 Mock 分页结果。

| 列 | 含义 |
| --- | --- |
| 覆盖需求 | 该用例验证的需求点，格式 `FR-NNN / AC-NNN / BR-NNN` |
| 前置条件 | 数据状态、角色、夹具规模与注入时钟等执行前必须成立的事实 |
| 步骤 | 编号化、可独立复现的操作序列（含非法请求构造） |

### 关键集成场景展开（Given / When / Then）

以下 5 条场景承载事务、并发与追溯的核心风险，展开为可直接落地的步骤与断言，执行时逐条核对断言要点。

**IT-003 报工事务整体回滚（事务边界）**

- Given：`WO-IT-0001` 累计已报 400、状态 `IN_PROGRESS`、剩余 100；`InspectionOrderService.createFromReport()` 被注入 `DataAccessResourceFailureException`
- When：`POST /api/work-orders/WO-IT-0001/actions` 提交 `action=REPORT`、`goodQty=100`、`scrapQty=0`、`version=3`
- Then：接口返回 409 与业务错误码；`SELECT good_qty_total, status FROM work_order WHERE work_order_no = 'WO-IT-0001'` 仍为 `400 / IN_PROGRESS`；`report_record` 计数 0；`work_order_state_history` 无新增
- 断言要点：报工与检验单生成必须处于同一 `@Transactional(rollbackFor = Exception.class)` 边界；异常不得被捕获后仍然提交

**IT-007 并发报工乐观锁（AC-006）**

- Given：`WO-IT-0007` 的 `version=3`、剩余可报 100；连接池上限 ≥ 4
- When：`CountDownLatch` 同步起跑两个请求，均携带 `version=3` 与 `goodQty=100`
- Then：结果集合恰为 `{HTTP 200, HTTP 409}`；409 载荷错误码为 `VERSION_CONFLICT`；最终 `good_qty_total = 500`、`version = 4`；报工记录 1 条
- 断言要点：乐观锁以 `UPDATE work_order SET good_qty_total = good_qty_total + :qty, version = version + 1 WHERE id = :id AND version = :version` 的影响行数为唯一判据，禁止「先查后写」的伪乐观锁

**IT-025 并发投料争抢批次（BR-012）**

- Given：批次 `LOT-IT-0025` 状态 `AVAILABLE`、剩余 1000；两个工单各需投料 800
- When：栅栏同步起跑两次 `POST /api/material-batches/LOT-IT-0025/feedings`（`feedQuantity=800`）
- Then：恰一个 HTTP 200、一个 HTTP 400 + `INSUFFICIENT_STOCK`；批次剩余 200；`feeding_record` 1 条；`remaining_qty >= 0` 恒成立
- 断言要点：扣减为单条原子 UPDATE（`WHERE remaining_qty >= :feed`）并以行级锁或乐观锁兜底，同时保留 `CHECK (remaining_qty >= 0)` 作为最后防线

**IT-029 正向追溯递归 CTE（AC-021）**

- Given：批次 `LOT-IT-0029` 已投料至 2 个工单，各产出 1 个成品；另构造 1 个工单缺少检验记录
- When：`GET /api/trace?traceDirection=FORWARD&materialBatchNo=LOT-IT-0029&page=1&size=50`
- Then：完整链路节点覆盖 投料批次 → 工单 → 成品 → 检验记录 四类；响应 `partial=true`，`brokenNodes` 含缺检验记录的工单号；结果集不超过分页上限
- 查询骨架：

```sql
WITH RECURSIVE trace AS (
    SELECT f.material_batch_no, f.work_order_no, f.feed_qty, 1 AS depth
    FROM feeding_record f
    WHERE f.material_batch_no = :materialBatchNo
    UNION ALL
    SELECT t.material_batch_no, f2.work_order_no, f2.feed_qty, t.depth + 1
    FROM trace t
    JOIN feeding_record f2 ON f2.work_order_no = t.work_order_no
    WHERE t.depth < 3
)
SELECT * FROM trace;
```

- 断言要点：`depth < 3` 上限防止数据环导致无限递归；断链节点由左连接的空值判定，不抛异常而是降级为 `partial`；执行计划命中 `idx_feeding_batch` 与 `idx_feeding_work_order`

**IT-013 排程冲突唯一约束兜底（BR-004）**

- Given：设备 `EQ-07` 已有 `09:00-11:00` 任务；两个重叠候选时段（`10:00-12:00`、`10:30-11:30`）并发提交
- When：栅栏同步起跑两次排程请求
- Then：恰一个 HTTP 200、一个 HTTP 409 + `SCHEDULE_CONFLICT`；`EQ-07` 任务数仍为 1 条，原任务时间未被修改
- 断言要点：即使应用层冲突检测被竞态窗口绕过，排他约束 `ex_schedule_task_equipment_period` 仍必须拒绝写入；数据库返回的 `23P01` 异常应被映射为 `SCHEDULE_CONFLICT` 而非 500

| 归档任务（超过 1 年的工单与报工迁至归档表） | 需要跨年度数据与调度窗口 | 归档任务逻辑由单元测试覆盖；端到端归档演练在试运行阶段执行 |

## §A 用例字段标准（系统级验收适用）

系统级验收时，用例采用九字段结构，便于与可追溯性矩阵、缺陷统计、覆盖率分析对齐：

| 字段 | 本项目的填写约定 |
| --- | --- |
| 编号 | `IT-<序号>` 全局唯一，与 `@test-id TEST-MES-<序号>` 一一对应 |
| 模块 | 一级业务模块，取值为 CAP-001 ~ CAP-005 或「横切能力」 |
| 子模块 | 二级功能分组，如「工单状态机」「批次库存」「检验判定」 |
| 用例名称 | 一句话概括测试目标，含可判定的结果动词（返回、回滚、拦截） |
| 前置条件 | 数据状态、角色与数据范围、夹具规模、注入时钟、外部依赖状态 |
| 操作步骤 | 编号化、可独立复现，含非法请求与约束绕过语句 |
| 预期结果 | 与步骤一一对应，覆盖 HTTP 状态码、错误码、数据库状态与审计记录 |
| 用例等级 | P0 阻断 / P1 严重 / P2 一般 / P3 建议 |
| 标签 | 归类标签，如「事务」「并发」「约束兜底」「性能」「迁移」「权限」 |

## §B 黑盒用例设计套路速查

设计与补测时按以下套路逐项覆盖，避免漏测：

- **等价类划分**：状态与枚举字段覆盖全部合法取值 + 1 个非法取值；金额与数量覆盖合法区间、0、负数、超精度。
- **边界值**：计划数量 1 / 100000、报工剩余量 100 / 101、设备离线 59s / 61s、告警升级 9 分钟 / 11 分钟、换型间隔 9:59 / 10:00、追溯区间 365 天 / 366 天、检验上下限闭区间与 ±0.01% 容差。
- **状态矩阵**：工单 9 态 × 关键事件（下达、排程、开工、暂停、报满、判定、关闭、取消）逐格覆盖；非法跳转与终态写操作独立用例。
- **约束矩阵**：应用层校验与数据库约束成对验证——唯一索引（工单号、批次号、事件窗口、设备时段、处置单）、CHECK（`remaining_qty >= 0`、`planned_qty > 0`）、外键、触发器（审计不可变）。
- **并发矩阵**：并发报工、并发排程、乱序上报、并发投料四类竞态各一条确定性用例，断言「恰好一个成功」。
- **流程穿插**：主流程「过程中」与「结束后」两类切入点均有用例（IT-003 在报工中回滚、IT-004 在关闭后拒绝写操作）。
- **持久化校验**：跨请求/跨会话后重新查询数据库，验证数据未丢失且状态未回退（IT-004、IT-019、IT-026）。
- **重复与压力**：重复提交同一操作、快速反复点击对应的幂等与限流行为（IT-020、IT-040）。
- **性能与计划**：先断言执行计划命中索引，再断言 P95/P99，避免用「加索引前的时延」冒充达标证据。
- **迁移与回滚**：空库、已有库、重复执行、回滚四象限各一条用例（IT-044、IT-046）。

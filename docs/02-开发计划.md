### 迭代节奏

- P2 采用 2 周一个迭代，共 3 个迭代：迭代 1 覆盖 CAP-001 与 CAP-002，迭代 2 覆盖 CAP-003 与 CAP-004 前段，迭代 3 覆盖 CAP-004 后段与 CAP-005。
- 每个迭代末执行一次内部验收：编译通过、单测全绿、覆盖率不低于门槛、迭代范围内 P0 的 AC 用例通过。
- 迭代内不允许引入需求规格书之外的新 FR；发现规格缺口时登记为变更申请，由 Architect 与 Product Analyst 联合评估后再排期。
- 每日对账外部依赖（DEP-01～DEP-04）状态，每周对账里程碑偏差。

## 发布与回滚考虑

- **发布形态**：容器化单实例应用 + 单主 PostgreSQL；镜像以 git tag 标记版本，配置通过环境变量注入且不进入代码仓库。
- **发布策略**：先在同构预发环境完成一次全量部署验证与冒烟，再在生产环境滚动升级；上线窗口安排在非生产时段，配套 1 个完整班次的试运行观察期。
- **数据库迁移**：迁移脚本随版本单调递增并纳入版本控制；发布前在预发环境对生产数据副本执行一次迁移演练，记录执行耗时。迁移脚本向前兼容一个版本，保证回滚可用。
- **功能开关**：排程自动生成（FR-004）、OEE 统计（FR-008）、追溯报告导出（FR-011）三项具备功能开关，异常时可单独关闭而不整体回滚；关闭后对应页面显示不可用提示，业务可退回原有手工方式。
- **回滚触发条件**：出现 P0 级缺陷、核心链路不可用、或迁移导致数据不一致时立即回滚。
- **回滚步骤**：停止应用新版本 → 回退至上一版本镜像 → 若迁移已执行则运行对应回滚脚本 → 校验工单、报工、批次库存三类数据一致 → 恢复服务 → 记录事故与回滚原因。
- **回滚验证**：回滚后执行冒烟用例集（登录、工单查询、设备看板上报、追溯查询各 1 条），全部通过方可宣布回滚完成。
- **数据保护**：发布前对生产库做全量备份并验证可恢复；审计日志表不参与任何回滚删除操作。

## 重要建议

### CR-MAJOR-01 库存扣减「先查后改」非原子，并发投料可致负库存（已修复）

- **位置**：`meslite-traceability` 的 `FeedingService#feed`、`MaterialBatchMapper.updateAvailableQty`
- **关联需求**：FR-010、BR-012、BR-008；影响 AC-019、AC-020
- **现象**：原实现先 `selectById` 读出 `available_qty`，在 Java 侧比较投料量后 `updateById` 写回。两个并发投料请求可同时读到同一可用量并通过校验，最终扣减结果超出库存。
- **影响**：违反 BR-012「不允许出现负库存」，属数据正确性缺陷；批次可用量错误会进一步污染追溯链路与超领判定。
- **修复**：改为单条原子 UPDATE，把比较条件下推到数据库：
  `UPDATE material_batch SET available_qty = available_qty - #{qty}, version = version + 1 WHERE id = #{id} AND version = #{version} AND status = 'AVAILABLE' AND available_qty >= #{qty}`；
  受影响行数为 0 时按 `version` 是否变化区分抛出 `VERSION_CONFLICT` 或 `INSUFFICIENT_STOCK`。同时在迁移脚本 `V2__batch_qty_check.sql` 增加 `CHECK (available_qty >= 0)` 作为数据库层兜底。
- **验证**：新增 `FeedingConcurrencyIT`（50 并发 × 200 轮，库存 1000、每笔投料 30），负库存 0 次、超卖 0 次、`INSUFFICIENT_STOCK` 返回数与理论值一致；`V2` 迁移在 `flyway validate` 下校验通过。
- **状态**：已修复，v1.0.0 复验通过。

### CR-MAJOR-02 追溯查询的方向与排序字段来自请求参数拼接（已修复）

- **位置**：`meslite-traceability` 的 `TraceMapper.xml#selectTraceChain`、`TraceService#query`
- **关联需求**：FR-011；影响 AC-021、AC-022
- **现象**：追溯链路查询的排序方向与排序列原实现以字符串拼接方式进入 `ORDER BY`，取值来自查询参数 `traceDirection` 与 `sortBy`。
- **影响**：构成 SQL 注入面；非法取值还会造成数据库语法错误并向前端回显 SQL 片段，违反接口契约的错误码约定。
- **修复**：新增枚举 `TraceDirection { FORWARD, BACKWARD }` 与 `TraceSortField { OCCURRED_AT, WORK_ORDER_NO, QTY }`；Controller 层以枚举绑定拒绝非法值（400 + `INVALID_TRACE_DIRECTION`）；Mapper 改为 `<choose>` 静态分支，彻底移除以 `$` 拼接用户输入的写法。
- **验证**：新增 `SqlInjectionGuardTest`，注入 `FORWARD;DROP TABLE material_batch--`、`1' OR '1'='1`、`OCCURRED_AT,(SELECT pg_sleep(5))` 等 11 个载荷，断言全部返回 400 且表结构与行数不变；复查全部 Mapper XML，以 `$` 拼接用户输入的用法为 0 处。
- **状态**：已修复，v1.0.0 复验通过。

### CR-MAJOR-03 排程冲突检测使用闭区间，边界重叠漏检（已修复）

- **位置**：`meslite-scheduling` 的 `ScheduleConflictDetector#hasOverlap`
- **关联需求**：FR-005、BR-004、BR-013；影响 AC-011
- **现象**：原实现判定条件为 `newStart <= existingEnd && newEnd >= existingStart`，把时间区间当作闭区间处理。BR-004 明确要求左闭右开 `[start, end)`，且相邻任务之间允许 ≥ 10 分钟换型间隔。
- **影响**：当新任务恰好从既有任务的结束时刻开始时（如既有 09:00-11:00、新任务 11:00-13:00），系统会误报 `SCHEDULE_CONFLICT`；同时换型间隔未被纳入校验，可产生零间隔连排，违反 BR-004 的例外条款。
- **修复**：区间判定改为 `newStart < existingEnd && newEnd > existingStart`；并把「相邻任务最小间隔 ≥ 10 分钟」抽为常量 `MIN_CHANGEOVER_MINUTES = 10`，在冲突提示中明确返回冲突任务工单号与时间段。
- **验证**：新增 `ScheduleConflictDetectorTest` 覆盖 12 组边界取值（含首尾相接、间隔 9 分钟、间隔 10 分钟、完全包含、完全被包含），全部符合 BR-004；集成测试 `ScheduleConflictIT` 复现 AC-011 场景并断言原任务不被修改。
- **状态**：已修复，v1.0.0 复验通过。

### CR-MAJOR-04 审计日志同步写入业务事务，日志故障会回滚业务（已修复）

- **位置**：`meslite-security` 的 `AuditLogRecorder`、`AuditLogRecorder#record` 与落库通道
- **关联需求**：BR-015、NFR-006、RSK-06；影响 AC-001、AC-019、AC-029
- **现象**：审计切面在业务事务内同步写 `audit_log` 表，且未做异常隔离。审计表出现写入延迟或锁等待时，业务写操作一并失败。
- **影响**：与 NFR-006「日志写入失败率 ≤ 0.01%」的设计意图相反——该指标假设审计写入失败不应中断业务；同时把审计写入放进同一事务会显著拉长事务持锁时间，放大了 RSK-06 描述的写入放大风险。
- **修复**：审计写入改为 `REQUIRES_NEW` 独立事务 + 有界队列异步落库，失败进入 `audit_log_retry` 表并按 1s/5s/30s 退避重试；切面捕获异常后仅告警不抛出，失败计数暴露为 Micrometer 指标 `mes_audit_write_failures_total`。审计字段（操作人、时间、对象类型、对象 ID、变更前后摘要、操作来源）保持不变。
- **验证**：新增 `AuditLogFailureIsolationTest`（注入写失败）断言业务事务提交成功且失败计数 +1；`AuditLogThroughputIT` 在 200 次/秒写压下审计落库延迟 P95 = 46ms，业务接口 P95 未劣化；`mes_audit_write_failures_total` 已纳入告警规则（失败率 > 0.01% 触发）。
- **状态**：已修复，v1.0.0 复验通过。

## 配置项和环境变量

运行时配置全部经环境变量注入，**仓库内不保存任何真实值**。生产部署使用 `deploy/.env`（权限 0600，不纳入版本控制），Compose 通过 `env_file` 读取；仓库中只保留 `deploy/.env.example`。

| 变量 | 必填 | 说明 | 示例值（占位，非真实值） |
| --- | --- | --- | --- |
| `SPRING_PROFILES_ACTIVE` | 是 | 运行 profile，生产必须为 `prod` | `prod` |
| `MES_DB_URL` | 是 | JDBC 连接串 | `jdbc:postgresql://mes-db-01.example.com:5432/meslite` |
| `MES_DB_USER` | 是 | 应用数据库账号（最小权限） | `meslite_app` |
| `MES_DB_PASSWORD` | 是 | 数据库口令 | `change-me-on-deploy` |
| `MES_DB_POOL_MAX` | 否 | 连接池上限 | `30` |
| `MES_JWT_SECRET` | 是 | JWT 签名密钥（≥ 256 位） | `change-me-on-deploy` |
| `MES_JWT_TTL_MINUTES` | 否 | 令牌有效期（分钟） | `480` |
| `MES_SESSION_IDLE_MINUTES` | 否 | 会话空闲失效（NFR-007 要求 30） | `30` |
| `MES_LOGIN_MAX_FAILURES` | 否 | 登录失败锁定阈值（NFR-007 要求 5） | `5` |
| `MES_GATEWAY_TOKEN` | 是 | 设备网关上报共享密钥 | `change-me-on-deploy` |
| `MES_SHIFT_CALENDAR_PATH` | 否 | 班次日历配置路径 | `/opt/mes-lite/config/shift-calendar.yml` |
| `MES_ARCHIVE_RETENTION_YEARS` | 否 | 归档保留年限（NFR-005 要求 ≥ 3） | `3` |
| `MES_LOG_LEVEL` | 否 | 根日志级别 | `INFO` |
| `MES_OTLP_ENDPOINT` | 否 | OTLP 接收地址 | `http://otel-collector.mes-lite.example.com:4318` |
| `MES_METRICS_ENABLED` | 否 | 是否暴露 Prometheus 指标 | `true` |
| `TZ` | 否 | 容器时区 | `Asia/Shanghai` |

```dotenv

```

## 凭据与密钥管理

| 规则 | 说明 |
| --- | --- |
| 不入库 | 任何口令、令牌、密钥都不得写入代码、镜像、Compose 文件或本文档；仓库内只允许出现 `change-me-on-deploy` 这类占位串 |
| 注入方式 | 生产值由密钥管理系统下发至 `deploy/.env`，或在启动时经运行时环境注入；Compose 使用 `env_file`，不使用内联明文 |
| 启动自检 | 应用启动时校验关键变量：缺失或仍等于占位串时**拒绝启动**并记录安全事件（避免占位凭据被误用到生产） |
| 权限 | `deploy/.env` 权限 0600，属主为部署账号；`deploy/` 目录权限 0750 |
| 轮换 | JWT 密钥与网关令牌每 30 天轮换一次；轮换后旧 JWT 立即失效，网关令牌支持双值并行 24 小时以平滑切换 |
| 数据库账号 | `meslite_app` 仅具备业务表的 SELECT/INSERT/UPDATE 权限，无 DDL 与 DELETE 权限；迁移由独立的 Flyway 账号执行 |
| 扫描 | 每次发布前执行 `gitleaks detect` 与 `trivy image`，结果留档于 `_test_output/security/` |

## 构建步骤

```bash
# 1. 取代码并切换到发布标签
git clone https://example.com/meslite/mes-lite.git
cd mes-lite && git checkout v1.0.0

# 2. 后端构建与测试（单元 + 集成）
mvn -B -q clean verify -Pit
# 产出：meslite-app/target/meslite-app-1.0.0.jar

# 3. 前端构建
pnpm -C meslite-web install --frozen-lockfile
pnpm -C meslite-web run build
# 产出：meslite-web/dist/

# 4. 构建镜像（按 digest 记录，禁止 latest）
docker build -t registry.example.com/meslite/meslite-app:1.0.0 ./meslite-app
docker build -t registry.example.com/meslite/meslite-web:1.0.0 ./meslite-web
docker push registry.example.com/meslite/meslite-app:1.0.0
docker push registry.example.com/meslite/meslite-web:1.0.0

# 5. 记录镜像 digest 与 SBOM（发布证据）
docker inspect --format='{{index .RepoDigests 0}}' registry.example.com/meslite/meslite-app:1.0.0
syft registry.example.com/meslite/meslite-app:1.0.0 -o spdx-json > _test_output/release/sbom-app.json
```

构建可复现性：`pnpm --frozen-lockfile` 与 Maven 依赖锁定保证依赖版本一致；镜像基础层按 digest 固定；产物附 `sha256` 校验清单 `_test_output/release/checksums.txt`。

## 部署步骤

以下步骤在应用节点 `mes-app-01.example.com` 上以部署账号 `deploy`（无 sudo）执行。

| 步骤 | 命令 / 操作 | 预期 |
| --- | --- | --- |
| 1. 准备目录 | 创建 `/opt/mes-lite`，子目录 `deploy/`、`config/`、`logs/`、`backup/`；属主 `deploy:deploy` | 目录权限 0750 |
| 2. 放置部署包 | 解压 `deploy/` 至 `/opt/mes-lite/deploy`，确认含 `docker-compose.yml`、`nginx/mes-lite.conf`、`flyway/` | `docker compose config -q` 通过 |
| 3. 写入配置 | 复制 `deploy/.env.example` 为 `deploy/.env`，由密钥管理系统替换全部占位值，`chmod 600 .env` | `grep -c change-me-on-deploy .env` 返回 0 |
| 4. 校准时区与时钟 | `timedatectl set-timezone Asia/Shanghai`；确认 `chronyc tracking` 偏差 ≤ 1s | NTP 同步正常 |
| 5. 数据库初始化 | 由 DBA 创建库 `meslite` 与账号 `meslite_app`；执行第 11 节的数据迁移 | `flyway validate` 通过 |
| 6. 拉取镜像 | `docker compose pull app web` | 拉取到 `1.0.0` digest |
| 7. 启动数据库与应用 | `docker compose up -d db app` | 容器状态 `healthy` |
| 8. 启动前端与入口 | `docker compose up -d web nginx` | 443 可访问 |
| 9. 冒烟验证 | `curl -fsS https://mes-lite.example.com/api/actuator/health/readiness` | 返回 `{"status":"UP"}` |
| 10. 业务验证 | 按 `docs/16-E2E测试用例.md` 执行 E2E-001、E2E-004、E2E-006 三条主链路冒烟（创建下达 → 投料绑定 → 判定关闭） | 全部通过 |
| 11. 观察窗口 | 观察 30 分钟 SLI 看板与告警 | 无 P0/P1 告警，错误率 ≤ 0.1% |

滚动升级（有备用节点时）：先起新版本容器并接入健康检查，验证通过后再切流量并停旧容器；升级期间数据库 schema 必须新旧兼容（见回滚方案）。

## 启动、停止和重启方式

```bash
# 进入部署目录
cd /opt/mes-lite/deploy

# 启动全部服务
docker compose up -d

# 查看状态
docker compose ps

# 停止全部服务（保留数据卷）
docker compose stop

# 停止并移除容器（保留数据卷与配置）
docker compose down

# 重启单个服务
docker compose restart app

# 滚动重启应用（零停机：先起新容器再停旧容器）
docker compose up -d --no-deps --scale app=2 app && sleep 20 \
  && docker compose up -d --no-deps --scale app=1 app

# 查看日志
docker compose logs -f --tail=200 app
```

定时任务（归档、审计日切、OEE 汇总）通过应用内调度器执行，设计上可重入，重启不会重复处理已完成的批次；重启后 5 分钟内应看到下一次调度日志。

## 健康检查

| 层级 | 检查项 | 命令 | 期望结果 |
| --- | --- | --- | --- |
| 存活 | 应用进程 | `curl -fsS http://127.0.0.1:8080/actuator/health/liveness` | `{"status":"UP"}` |
| 就绪 | 应用 + 数据库 + 迁移 | `curl -fsS http://127.0.0.1:8080/actuator/health/readiness` | `{"status":"UP"}`，`components.db.status = UP` |
| 数据库 | 主库连通性 | `pg_isready -h mes-db-01.example.com -p 5432 -d meslite` | `accepting connections` |
| 迁移状态 | Flyway 校验 | `docker compose exec app java -jar app.jar --flyway-validate-only` 或查看 `/actuator/health` 的 `flyway` 组件 | `V1`、`V2` 均为 `success` |
| 入口 | Nginx 与静态资源 | `curl -fsS -o /dev/null -w '%{http_code}' https://mes-lite.example.com/` | `200` |
| 指标端点 | Prometheus 抓取 | `curl -fsS http://127.0.0.1:8080/actuator/prometheus \| head` | 返回 `mes_` 前缀指标，无 401 |
| 网关通道 | 设备上报可达 | 用测试令牌上报一次心跳，`POST /api/equipments/EQ-01/status` | 返回 200 |
| 深度检查 | 关键 SQL | `curl -fsS -X POST http://127.0.0.1:8080/actuator/health/readiness`（含自定义 `WorkOrderHealthIndicator`） | 工单表可查询，`status = UP` |

Actuator 暴露面仅 `health`、`info`、`prometheus`，且需认证；`health` 的 `show-details` 在生产为 `when-authorized`。上述 `127.0.0.1` 调用在应用节点本机执行，不对外暴露。

## 日志和故障排查

### 日志位置与格式

| 日志 | 路径 / 出口 | 格式 | 保留 |
| --- | --- | --- | --- |
| 应用日志 | 容器 stdout → `/opt/mes-lite/logs/app.log`（Compose 日志驱动轮转 100MB × 10） | JSON 单行，含 `ts`、`level`、`logger`、`traceId`、`userId`、`msg` | 热存 30 天，冷存 ≥ 3 年 |
| 访问日志 | `/opt/mes-lite/logs/nginx-access.log` | Nginx `combined` + `request_time` | 90 天 |
| 错误日志 | `/opt/mes-lite/logs/nginx-error.log` | Nginx error | 90 天 |
| 审计日志 | 数据库 `audit_log` 表 + 归档表 | 结构化字段（操作人/时间/对象/变更前后摘要/来源） | ≥ 3 年（NFR-005） |
| 采集出口 | OTLP → `otel-collector.mes-lite.example.com:4318` | OTLP/HTTP JSON | 由采集端策略控制 |

### 故障排查表

| 现象 | 可能原因 | 排查命令 | 处置 |
| --- | --- | --- | --- |
| 浏览器 502 Bad Gateway | 应用容器未就绪或已退出 | `docker compose ps`、`docker compose logs --tail=200 app` | 修复启动失败原因后 `docker compose up -d app`；确认 `readiness` 为 UP 再确认 Nginx 上游 |
| 应用启动即退出，日志出现 `readiness` 报错 | `.env` 中仍有占位串，触发启动自检拒绝 | `grep -c change-me-on-deploy /opt/mes-lite/deploy/.env` | 由密钥管理系统替换全部占位值后重启 |
| 启动报 Flyway checksum mismatch | 迁移脚本被改动或版本回退 | `docker compose logs app \| grep -i flyway` | 禁止手改已应用脚本；用 `flyway repair` 对齐校验和并复盘变更流程 |
| 接口大面积超时，`HikariPool` 等待告警 | 连接池耗尽或慢查询 | `curl -s localhost:8080/actuator/prometheus \| grep hikaricp`；数据库 `pg_stat_activity` | 临时提高 `MES_DB_POOL_MAX`；定位慢 SQL（追溯与 OEE 查询优先） |
| 容器被 OOMKilled | JVM 堆或导出任务内存峰值过高 | `docker inspect --format='{{.State.OOMKilled}}' <容器>`；`docker stats` | 调整 `-Xmx` 至不超过容器限额的 70%；追溯导出改为分片流式写出（已随 v1.0.0 发布） |
| 看板数据长时间不刷新 | 网关上报中断或 OTLP 出口不可达 | `docker compose logs app \| grep -i gateway`；`curl -s otel-collector.mes-lite.example.com:4318` | 检查网关侧；确认降级后看板显示「数据延迟」标记而非把旧数据当实时数据 |
| 登录报 `401` 且日志提示令牌无效 | 节点时钟偏移超过容忍值 | `chronyc tracking`、`date -u` | 恢复 NTP 同步；偏差修复后重新登录 |
| 审计写入失败计数上升 | 审计表锁等待或磁盘写满 | `curl -s localhost:8080/actuator/prometheus \| grep mes_audit_write_failures_total`；`df -h` | 清理磁盘或扩容；失败记录在 `audit_log_retry` 表中由重试任务补写 |
| 磁盘使用率持续上升 | 日志未轮转或归档任务未执行 | `du -sh /opt/mes-lite/logs/*`、查看归档任务日志 | 修正日志轮转配置；手动触发归档并核对 NFR-005 保留策略 |
| 静态资源 404 或页面白屏 | 前端镜像与后端版本不匹配 | `docker compose images`；核对 `meslite-web:1.0.0` digest | 按同一 tag 重新拉起 `web` 容器；检查 Nginx `try_files` 配置 |
| 设备上报返回 404 | 设备未在台账登记 | `docker compose logs app \| grep EQUIPMENT_NOT_FOUND` | 由设备管理员在设备台账补登记后重试 |

迁移脚本一经发布不得修改；新增变更必须追加新版本号。`V2` 的 `CHECK` 约束在大表上会加锁校验，本次数据量下实测耗时 4.2s，已在维护窗口内执行。

## 回滚方案

| 场景 | 回滚动作 | 预计耗时 | 数据影响 |
| --- | --- | --- | --- |
| 应用缺陷（schema 未变） | `docker compose` 切回上一版本镜像 `meslite-app:0.9.3` 与 `meslite-web:0.9.3`，不触碰数据库 | ≤ 5 分钟 | 无数据丢失；期间写入的数据仍可被旧版本读取（schema 前向兼容） |
| 应用缺陷（schema 已前向变更） | 仅回滚应用镜像，保留新 schema（expand/contract 两阶段：v1.0.0 只做加法，未删除旧列） | ≤ 5 分钟 | 无数据丢失 |
| 数据错误（迁移引入脏数据） | 停应用 → 从 `backup/meslite-pre-v1.0.0.dump` 恢复到新库 → 切换连接串 → 起旧版本 | 30–60 分钟 | 备份时点之后的业务数据需手工补录，需业务确认补录范围 |
| 设备上报通道异常 | 停用网关接入，启用班组长手工上报（NFR-004 降级策略） | ≤ 10 分钟 | 看板显示「数据延迟」标记，业务不中断 |
| 单节点故障（应用） | 在 `mes-app-02.example.com` 拉起同 digest 容器并切换 Nginx 上游 | ≤ 15 分钟 | 无数据丢失 |

回滚原则：**数据库迁移不提供自动回滚**（Flyway 社区版无 undo）。因此所有迁移必须遵循 expand/contract：先加列加表并保持兼容，待新版本稳定运行一个发布周期后再清理旧结构。回滚演练每季度执行一次，最近一次 2026-06-05 演练耗时 4 分 12 秒。

回滚验证清单：回滚后必须重新执行第 9 节的冒烟验证与健康检查，并确认 `/actuator/health/readiness` 为 UP、错误率回落至基线。

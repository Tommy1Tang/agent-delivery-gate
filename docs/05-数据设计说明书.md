## 1. 设计范围

- **涉及数据库**：PostgreSQL 16 单主库，逻辑库名 `meslite`，部署实例以符号名 `mes-db-01.example.com` 指代（端口 `5432`，不对应任何真实主机）。
- **涉及表/集合**：
  - 基线表 24 张：`work_order`、`work_order_operation`、`work_order_report`、`production_schedule`、`work_center`、`shift_calendar`、`equipment`、`equipment_status_log`、`equipment_alarm`、`equipment_downtime`、`material`、`material_batch`、`batch_feeding`、`inspection_order`、`inspection_item`、`nonconformity`、`disposal_order`、`audit_log`、`idempotency_record`、`outbox_event`、`sys_user`、`sys_role`、`user_role`、`dict_item`。
  - 24 张的构成口径：**19 张业务表**（前 19 项，与 `docs/18-部署说明.md`「19 张业务表」及 `docs/19-监督审计.md` 口径一致）＋ **3 张权限表**（`sys_user`、`sys_role`、`user_role`）＋ **2 张平台表**（`idempotency_record`、`outbox_event`）。
  - 归档与派生表 3 张：`work_order_archive`、`work_order_report_archive`、`oee_daily`（`oee_daily` 依据 `docs/06-性能优化说明.md` OPT-007）。
  - 年分区：`equipment_status_log`、`audit_log` 按 `occurred_at` 逐年分区（ADR-004）。
- **数据量级预估**（依据 `docs/01-需求规格书.md` 约束与依赖「工单 5 万条/年、投料记录 100 万条/年、设备状态变更记录 200 万条/年」）：
  - 当前：0 行（新建系统，交付前仅初始化主数据）。
  - 1 年内：`work_order` 5 万行；`batch_feeding` 100 万行；`equipment_status_log` 200 万行；`audit_log` 150 万行；全部表合计约 1450 万行、约 1.4 GB。
  - 3 年内：`equipment_status_log` 约 600 万行（0.9 GB）；`audit_log` 约 450 万行（2.2 GB）；`batch_feeding` 约 300 万行；仍无单表需要分片。
- **范围内**：24 张基线表的字段、类型、可空性、默认值、主键 / 外键、状态枚举 `CHECK` 约束与唯一约束；索引与分区设计；状态机的持久化方式；数据一致性、幂等与并发控制；迁移脚本规划与回滚；归档与清理；查询优化建议；数据库账号权限划分。
- **范围外**（原因见 `docs/04-详细设计说明书.md` 1.3）：
  - ERP / 财务 / 采购系统的数据落地与同步表——需求范围外，不设集成适配层。
  - 数据仓库、BI 宽表与离线主题域——OEE 与负荷在应用内聚合，不建数仓。
  - 多工厂 / 多组织的租户隔离字段——单工厂单组织，表结构不预留租户列。
  - 统计过程控制（SPC）模型表——仅落检验数据与判定结果。
  - 移动端与扫码枪的独立存储——复用同一套表，仅录入方式不同。

## 2. 实体关系设计

### 2.1 ER 图（或实体关系描述）

```text
[work_center]     --1:N--> [work_order] / [equipment]
[work_order]      --1:N--> [work_order_operation] / [work_order_report] / [batch_feeding]
[work_order]      --1:N--> [inspection_order] / [nonconformity]
[production_schedule] --N:1--> [work_order] / [equipment]
[equipment]       --1:N--> [equipment_status_log] / [equipment_alarm] / [equipment_downtime] / [oee_daily]
[material]        --1:N--> [material_batch] --1:N--> [batch_feeding]
[inspection_order] --1:N--> [inspection_item] / [nonconformity] --1:N--> [disposal_order]
[sys_user]        --1:N--> [user_role] --N:1--> [sys_role]
[sys_user]        --1:N--> [audit_log]
[batch_feeding] 为追溯边：正向（批次→工单）与反向（工单→批次）共用，见 2.2、4.4
[outbox_event] / [idempotency_record] / [dict_item] / [shift_calendar] 为支撑表，无强关联
```

### 2.2 关系详情

| 关系 | 类型 | 关联字段 | 参照完整性策略 | 备注 |
|------|------|----------|----------------|------|
| `work_order_operation` → `work_order` | 1:N | `work_order_id` → `work_order.id` | 外键 + `ON DELETE CASCADE` | 工序快照随工单物理删除而清理（04 §5.4 允许的三个级联例外之一） |
| `work_order_report` → `work_order` | 1:N | `work_order_id` → `work_order.id` | 外键 + `ON DELETE CASCADE` | 报工明细，随工单聚合根管理 |
| `inspection_item` → `inspection_order` | 1:N | `inspection_id` → `inspection_order.id` | 外键 + `ON DELETE CASCADE` | 检验项，随检验单聚合根管理 |
| `batch_feeding` → `work_order` | 1:N | `work_order_id` → `work_order.id` | 应用层保证 | 生产记录受 NFR-005 保护，不允许级联删除（BR-009） |
| `batch_feeding` → `material_batch` | N:1 | `material_batch_no` → `uk_mbn` | 应用层保证 | 以业务唯一键而非代理键关联，保证追溯链路可读 |
| `production_schedule` → `work_order` / `equipment` | N:1 | `work_order_id`、`equipment_id` | 应用层保证 | 同设备时段不重叠由 GiST 排他约束保证（BR-004） |
| `equipment_status_log` → `equipment` | 1:N | `equipment_id` → `equipment.id` | 应用层保证 | 年分区表，写入量最大（200 万行/年） |
| `equipment_alarm` / `equipment_downtime` → `equipment` | 1:N | `equipment_id` → `equipment.id` | 应用层保证 | 告警未关闭不可删（BR-007） |
| `material_batch` → `material` | N:1 | `material_code` → `uk_material_code` | 应用层保证 | 以业务键关联，主数据可独立演进 |
| `inspection_order` → `work_order` | N:1 | `work_order_id` → `work_order.id` | 应用层保证 | 来料检验该列为空，改填 `material_batch_no` |
| `nonconformity` → `inspection_order` | N:1 | `inspection_id` → `inspection_order.id` | 应用层保证 | 判定 FAIL 时生成（FR-013） |
| `disposal_order` → `nonconformity` | N:1 | `nonconformity_id` → `nonconformity.id` | 应用层保证 | 同一不合格记录同时只允许 1 张未关闭处置单（FR-014 E3） |
| `audit_log` → `sys_user` | N:1 | `operator_id` → `sys_user.id` | 应用层保证 | 只追加；操作人停用后仍保留原始 ID |
| `user_role` → `sys_user` / `sys_role` | N:M 中间表 | `user_id`、`role_id` | 外键约束 | ROLE-01 与 ROLE-04 互斥在服务层校验（BR-014） |

**不使用外键的通用理由**：04 §5.4 约定「除 `work_order_operation` / `work_order_report` / `inspection_item` 外不使用外键级联删除，完整性由业务逻辑负责」。数据层据此执行：生产与审计记录在保留期内禁止物理删除（NFR-005、NFR-006），外键级联在此场景下不仅无收益，还会隐藏误删；同时 `equipment_status_log` 为年分区表，跨分区外键校验会放大高频上报的写入成本（NFR-002 单条 ≤ 200ms）。

## 3. 表结构设计

### 3.1 通用字段与命名约定

**命名约定**：表名与列名一律 `snake_case`、单数、全小写；表名不带业务前缀（模块归属见表 3.14）；主键统一 `id`；业务唯一约束 `uk_`、普通索引 `idx_`、排他约束 `excl_`、BRIN 索引 `brin_`；时间列以 `_at` 结尾、日期列以 `_date` 结尾、数量列以 `_qty` 结尾。枚举取值一律大写英文，与 `docs/01-需求规格书.md` 及 `docs/07-接口数据契约.md` 8.1 完全一致。

**主键策略**：全部表使用 `BIGINT` 主键，取值由应用侧雪花算法生成（04 §5.2）。理由：避免 UUID 的索引膨胀与随机写放大；`equipment_status_log` 与 `audit_log` 年写入量达百万级，顺序性主键对 B-tree 与分区裁剪更友好；对外业务键（`wo_no`、`material_batch_no`、`inspection_no`）另设唯一索引，不承担物理定位职责。不使用 `IDENTITY`，避免应用与数据库两套发号器。

**公共审计字段**：除追加型表 `equipment_status_log`、`audit_log`、`outbox_event`、`idempotency_record`（仅保留 `created_at`）外的全部基线表，末尾统一带下列 6 列（本节 3.2 ~ 3.13 的字段表不再逐表重复，DDL 中逐个表显式声明）：

| 字段名 | 类型 | 长度/精度 | 可空 | 默认值 | 注释 |
|--------|------|-----------|------|--------|------|
| `created_at` | TIMESTAMP | 6 | NOT NULL | `now()` | 创建时间 |
| `updated_at` | TIMESTAMP | 6 | NOT NULL | `now()` | 更新时间 |
| `created_by` | BIGINT | - | NULL | NULL | 创建人 `sys_user.id`；系统任务写 `0` |
| `updated_by` | BIGINT | - | NULL | NULL | 更新人 `sys_user.id`；系统任务写 `0` |
| `is_deleted` | SMALLINT | 1 | NOT NULL | 0 | 软删除：0=正常 1=已删除；`CHECK (is_deleted IN (0,1))` |
| `version` | INTEGER | - | NOT NULL | 0 | 乐观锁版本号，每次写操作 +1 |

**约定细则**：

1. **时间**：全部时间列使用 `TIMESTAMP`（无时区），统一按 `Asia/Shanghai` 解释与写入，与班次日历、OEE 统计口径一致（04 §5.2）。数据库会话参数固定 `TimeZone = 'Asia/Shanghai'`，接口层输出 ISO-8601 无偏移量字符串。
2. **布尔**：以 `SMALLINT`（0/1）存储并加 `CHECK (col IN (0,1))`，与既有适配器约定一致，避免与 `is_deleted` 语义混淆（04 §5.2）。
3. **数量**：一律 `NUMERIC(18,3)`，满足 FR-009「最多 3 位小数」；禁止 `FLOAT` / `DOUBLE PRECISION`，避免库存扣减出现浮点误差（BR-012）。检验项上下限与实测值精度提高到 `NUMERIC(18,4)`，以承载 BR-010 的 ±0.01% 容差判定。
4. **软删除**：删除即置 `is_deleted = 1`，查询默认追加 `is_deleted = 0`。`work_order_report`、`batch_feeding`、`audit_log`、`equipment_status_log` 四张表不提供删除入口，禁止物理删除生产与审计记录（NFR-005、NFR-006）。
5. **乐观锁**：`work_order.version`、`material_batch.version`、`inspection_order.version` 由 `OptimisticLockerInnerInterceptor` 维护；更新影响行数为 0 时统一抛 `VERSION_CONFLICT`（HTTP 409），对应 AC-006。
6. **唯一性与软删除共存**：所有业务唯一键使用 `WHERE is_deleted = 0` 部分唯一索引，使软删除后的工单号 / 批次号可复用而不破坏历史可读性。
7. **列命名对账**：库存可用量列在 04 §5.3 中为 `qty_available`，本文件以该名称为准；`docs/14-代码评审.md`、`docs/18-部署说明.md`、`docs/可观测性报告.md` 中出现的 `available_qty` 为同一列的旧别名，需统一为 `qty_available`（含监控指标名 `mes_batch_qty_available`）。
8. **注释**：所有表与列必须带 `COMMENT ON`（中文），便于 DBA 与排查工具直接阅读，迁移脚本 V1 内一次性补齐。

### 3.2 表：`work_order`（工单主表）

| 字段名 | 类型 | 长度/精度 | 可空 | 默认值 | 注释 |
|--------|------|-----------|------|--------|------|
| `id` | BIGINT | - | NOT NULL | 雪花 ID | 主键 |
| `wo_no` | VARCHAR | 16 | NOT NULL | - | 工单号：`WO` + `yyyyMMdd` + 4 位流水（FR-001） |
| `product_code` | VARCHAR | 32 | NOT NULL | - | 产品物料编码，4-32 位大写字母/数字/连字符 |
| `planned_qty` | INTEGER | - | NOT NULL | - | 计划数量，1 ~ 100000 |
| `good_qty` | INTEGER | - | NOT NULL | 0 | 累计合格数量 |
| `scrap_qty` | INTEGER | - | NOT NULL | 0 | 累计报废数量 |
| `unit` | VARCHAR | 8 | NOT NULL | - | 单位：`PCS`/`SET`/`KG`/`M`/`L` |
| `status` | VARCHAR | 16 | NOT NULL | `CREATED` | 工单状态，9 值枚举（BR-002） |
| `priority` | VARCHAR | 8 | NOT NULL | `NORMAL` | 优先级：`LOW`/`NORMAL`/`HIGH`/`URGENT` |
| `work_center_id` | BIGINT | - | NULL | NULL | 工作中心 `work_center.id` |
| `planned_start_time` | TIMESTAMP | 6 | NOT NULL | - | 计划开始时间，≥ 创建时间 + 2 小时 |
| `planned_end_time` | TIMESTAMP | 6 | NOT NULL | - | 计划结束时间，> `planned_start_time` |
| `actual_start_time` | TIMESTAMP | 6 | NULL | NULL | 实际开始时间，开工时写入 |
| `actual_end_time` | TIMESTAMP | 6 | NULL | NULL | 实际结束时间，关闭时必填 |
| `remark` | VARCHAR | 500 | NULL | NULL | 备注 |

**补充说明**：`CHECK (planned_qty BETWEEN 1 AND 100000 AND good_qty >= 0 AND scrap_qty >= 0 AND good_qty + scrap_qty <= planned_qty)` 将 BR-002 / FR-002 E3 下沉为数据库兜底；`CHECK (planned_end_time > planned_start_time)` 对应 FR-001 E2；终态 `CLOSED` / `CANCELLED` 必须带 `actual_end_time`（`ck_wo_terminal`）。`status` 只允许经 `WorkOrderStateMachine` 与 `updateStatusWithVersion` 更新（04 §10.5）；终态收到变更请求时应用层返回 409 并记 `*.terminal.rejected` 日志。

### 3.3 表：`work_order_operation`（工序清单快照）

| 字段名 | 类型 | 长度/精度 | 可空 | 默认值 | 注释 |
|--------|------|-----------|------|--------|------|
| `id` | BIGINT | - | NOT NULL | 雪花 ID | 主键 |
| `work_order_id` | BIGINT | - | NOT NULL | - | 工单 `work_order.id`，`ON DELETE CASCADE` |
| `seq_no` | INTEGER | - | NOT NULL | - | 工序顺序，≥ 1，工单内唯一 |
| `operation_code` | VARCHAR | 32 | NOT NULL | - | 工序编码，取自工艺路线（BR-001） |
| `standard_hours` | NUMERIC | 10,2 | NOT NULL | - | 标准工时（小时），> 0 |
| `inspection_required` | SMALLINT | 1 | NOT NULL | 1 | 是否需检验：0=免检 1=需检验（BR-005 例外） |

### 3.16 状态机持久化（ST-001 ~ ST-010）

状态迁移采用「迁移表 + `CHECK` 约束」双层强制（ADR-002、04 §10.5）：数据库 `CHECK` 约束保证 `status` 列**不可能**被写入非法取值；应用侧 `WorkOrderStateMachine.fire(current, event)` 保证**不可能**发生未定义的迁移。

| 迁移 ID | 前置状态 | 事件 | 后置状态 | 数据库层强制点 | 应用层强制点 |
|---------|----------|------|----------|----------------|--------------|
| ST-001 | `CREATED` | 下达 | `RELEASED` | `CHECK` 允许两值；`uk_wo_no` 保证工单唯一 | `WorkOrderService.release` + `MasterDataValidator`（BR-001） |
| ST-002 | `RELEASED` | 生成排程 | `SCHEDULED` | `excl_eq_slot` 拒绝同设备重叠 | `ScheduleService.generate` + `ScheduleConflictDetector`（BR-003、BR-004） |
| ST-003 | `SCHEDULED` | 开工 | `IN_PROGRESS` | `batch_feeding` 非空五要素证明已投料；写入 `actual_start_time` | `WorkOrderReportService.act` + `FeedingService`（BR-009） |
| ST-004 | `IN_PROGRESS` | 暂停 | `PAUSED` | `CHECK` 允许两值 | `act(PAUSE)` + 暂停原因非空校验 |
| ST-005 | `PAUSED` | 恢复 | `IN_PROGRESS` | `version` 乐观锁 | `act(RESUME)` + `DataScopeResolver`（BR-014） |
| ST-006 | `IN_PROGRESS` | 数量报满 | `PENDING_QC` | `CHECK (good_qty + scrap_qty <= planned_qty)` | `act(REPORT)` 报满判定 + 写 `outbox_event` |
| ST-007 | `PENDING_QC` | 判定不合格 | `BLOCKED` | `CHECK (status <> 'JUDGED_FAIL' OR judge_remark IS NOT NULL)` | `InspectionService.judge` + `NonconformityService.openOnFail` |
| ST-008 | `BLOCKED` | 返工处置通过 | `IN_PROGRESS` | `uk_do_nc_open` 保证处置单唯一开启 | `DisposalService.approve`（`REWORK`） |
| ST-009 | `PENDING_QC` | 判定合格并关闭 | `CLOSED` | `actual_end_time` 写入；`ck_wo_terminal` 约束终态 | `WorkOrderService.close` + BR-005 / BR-011 校验 |
| ST-010 | `CREATED` | 取消 | `CANCELLED` | `work_order_report` 无对应行的存在性校验 | `WorkOrderService.cancel` |

**终态保护**：`CLOSED`、`CANCELLED`（工单）与 `CONSUMED`、`RETURNED`、`SCRAPPED`（批次）为终态；`WorkOrderStateMachine` 的迁移表对终态不配置任何出边，任何请求抛 `WORK_ORDER_STATE_INVALID`（409）并记 `*.terminal.rejected` 日志。批次状态机（BAT-ST-001 ~ BAT-ST-007）与检验单状态机（INSP-ST-001 ~ INSP-ST-005）以同样方式落 `CHECK` 约束，取值集合见 3.15。

**乐观锁与并发报工（AC-006）**：`work_order.version` 是并发报工的唯一仲裁点。报工事务内执行
`UPDATE work_order SET good_qty = good_qty + ?, scrap_qty = scrap_qty + ?, status = ?, version = version + 1, updated_at = now() WHERE id = ? AND version = ? AND is_deleted = 0`，
影响行数为 0 时说明版本已被其他终端推进，抛出 `VERSION_CONFLICT`（409），B 端不重复累加合格数量；冲突重试 1 次后仍失败即返回 409（04 §12.2）。同一机制用于 `material_batch`（BR-012 库存扣减）与 `inspection_order`（判定不可覆盖）。`equipment.current_status` 不使用乐观锁，改用幂等键 + 事件时间戳判定，以承受 5s/台的高频上报。

| `uk_dict_item` | `dict_type`, `item_code` | 唯一索引 | 字典项唯一（报废原因、停机原因、单位） | `WHERE is_deleted = 0` |
| `idx_dict_type_sort` | `dict_type`, `sort_no` | 复合索引 | 字典下拉按类型加载并排序 | 前端字典缓存源 |

### 4.6 索引建设与维护原则

1. 大表索引一律 `CREATE INDEX CONCURRENTLY`，避免长时间持有写锁（NFR-008、06 §5.2）；排他约束不支持 `CONCURRENTLY`，需在维护窗口内建立。
2. 每张分区表的索引在**每个分区**上独立创建；分区滚动任务在建新分区时同步建索引，否则设备状态插入将失败（06 §7 将「次年分区缺失」判定为 Critical）。
3. 索引命名规则：唯一约束 `uk_<表缩写>_<列>`、普通索引 `idx_<表缩写>_<列>`、排他约束 `excl_<缩写>_<列>`、BRIN 索引 `brin_<缩写>_<列>`。表缩写沿用 04 §5.4 的既有写法（`wo`、`wor`、`ps`、`eq`、`esl`、`ea`、`ed`、`mbn`、`bf`、`io`、`ii`、`nc`、`do`、`al`、`oe`）。
4. 新增索引必须复测写入 P95：OPT-001 与 OPT-004 的索引已使报工与投料写入开销上升约 5%（06 §9）。
5. `pg_stat_statements` 与 `pg_stat_user_indexes` 按月复核，`idx_scan = 0` 且已存在满 1 个月的索引进入下线评审。

### 4.7 不建议索引的字段

| 字段 | 原因 |
|------|------|
| `remark`、`reason`、`judge_remark`、`supplier_name`（VARCHAR 长文本） | 长文本字段索引效率低，且仅作展示，不做等值或范围条件 |
| `is_deleted` | 区分度极低（仅 0/1），单独索引无意义；应作为部分索引的过滤条件使用 |
| `before_summary`、`after_summary`、`payload_json`（JSONB） | 审计与事件负载只读不按字段检索；如需查询应另建表达式索引，避免 GIN 索引放大写入 |
| `from_status` / `to_status`（单独） | 取值少、选择性低；状态分析走 `equipment_id + occurred_at` 组合后再过滤 |
| `planned_qty`、`quantity`、`feed_quantity`（数值） | 业务上无「按数量区间找单据」的查询模式，范围扫描收益低于维护成本 |
| `source_ip`（INET） | 仅内部留痕，不提供按地址检索入口（9.1） |
| `slot`（TSRANGE，单独） | 仅作为排他约束的组成列，无独立查询模式 |

### 5.2 变更 DDL 策略

- **执行方式**：Flyway 版本化迁移在应用启动时自动执行（18 §11），结构性变更在维护窗口手工执行；单实例 + 单主库，无需在线 DDL 中间件。
- **前后兼容原则（expand / contract）**：所有变更遵循「先加后删」——先加列 / 加表 / 加索引并保持双写兼容，待新版本稳定运行一个发布周期后再清理旧结构；禁止在同一次发布中同时加列与删除被依赖的旧列（NFR-008、18 §12）。
- **锁表风险评估**：

  | 操作 | 锁级别 | 评估与对策 |
  |------|--------|------------|
  | `ADD COLUMN`（常量默认值） | `ACCESS EXCLUSIVE`（元数据级，极短） | PostgreSQL 11+ 不重写表；必须设 `lock_timeout = '3s'` 防止排队阻塞 |
  | `ADD COLUMN`（易变默认值 / 存储生成列） | `ACCESS EXCLUSIVE` + 全表重写 | 禁止对 `equipment_status_log`、`audit_log`、`batch_feeding` 直接执行；改为「加可空列 → 分批回填 → 置 NOT NULL」 |
  | `ALTER COLUMN TYPE` | `ACCESS EXCLUSIVE` + 全表重写 | 大表一律禁止；以新列 + 双写 + 切换替代 |
  | `ADD CONSTRAINT ... CHECK` | `ACCESS EXCLUSIVE` + 全表校验 | 优先 `ADD CONSTRAINT ... NOT VALID` 再 `VALIDATE CONSTRAINT`（后者仅取 `SHARE UPDATE EXCLUSIVE`）；强约束在维护窗口执行 |
  | `CREATE INDEX` | `SHARE`（阻塞写入） | 一律改用 `CREATE INDEX CONCURRENTLY`；失败留下 `INVALID` 索引，须先 `DROP INDEX` 再重建 |
  | `CREATE / DROP INDEX CONCURRENTLY` | `SHARE UPDATE EXCLUSIVE` | 与 `statement_timeout` 冲突，脚本内临时置 `statement_timeout = 0` 并在 `lock_timeout` 保护下执行；`DROP` 为索引下线的回滚动作（06 §5.2） |
  | `ATTACH / DETACH PARTITION` | `ACCESS EXCLUSIVE`（父表级，短暂） | 年分区滚动窗口内执行；PostgreSQL 14+ 可用 `DETACH PARTITION CONCURRENTLY` 在线分离 |
- **冻结规则**：迁移脚本一经发布不得修改（Flyway 校验和强制），新增变更必须追加新版本号（18 §11「启动报 Flyway checksum mismatch」的处置口径）。

  equipment_downtime, equipment_alarm, equipment, production_schedule, shift_calendar, work_center,
  work_order_report, work_order_operation, work_order, user_role, sys_role, sys_user, dict_item,

**回滚原则**：生产库的结构回滚以「从迁移前逻辑备份恢复 + 切换连接串 + 启动旧版本」为主路径（18 §12，30–60 分钟），显式回滚 DDL 仅用于**新增且未被写入**的结构（新索引、新派生表、新约束）。`DROP TABLE` 仅允许在空库演练与集成测试环境执行，生产环境由 DBA 审批后逐条放行。

## 6. 数据一致性保证

### 6.1 事务边界

| 操作 | 事务范围 | 隔离级别 | 理由 |
|------|----------|----------|------|
| 创建工单 + 工序快照 | `WorkOrderService.createWorkOrder` | READ_COMMITTED | 单聚合写，无显式锁，`uk_wo_no` 兜底并发重复 |
| 工单下达 / 取消（ST-001、ST-010） | `WorkOrderService.release` / `cancel` | READ_COMMITTED | `SELECT ... FOR UPDATE` 锁工单行，防止重复推进状态 |
| 报工（含报满转待检，ST-006） | `WorkOrderReportService.act` | READ_COMMITTED | 累计数量 + 报工记录 + 状态迁移 + 发件箱 + 审计必须原子；乐观锁仲裁（AC-006） |
| 投料登记与库存扣减（FR-010） | `FeedingService.feed` | READ_COMMITTED | 批次行锁 + 乐观锁扣减，`CHECK (qty_available >= 0)` 兜底（BR-012）；多批次按 `material_batch_no` 升序加锁 |
| 排程生成 / 调整（FR-004、FR-006） | `ScheduleService.generate` / `reschedule` | READ_COMMITTED | 排他约束 + 冲突预检；单事务排入不超过 50 个工单（AC-009） |
| 设备状态上报（FR-007） | `EquipmentService.reportStatus` | READ_COMMITTED | 幂等唯一索引短路；事务内不做看板聚合，保证单条 ≤ 200ms（NFR-002） |
| 检验录入 / 判定（FR-012、FR-013） | `InspectionService.saveItems` / `judge` | READ_COMMITTED | 检验项 + 检验单状态 + 不合格记录 + 工单 `BLOCKED` 同事务；乐观锁防覆盖 |
| 处置审批（FR-014） | `DisposalService.approve` | READ_COMMITTED | 审批状态 + 批次状态 + 工单状态联动；不跨能力域直接写工单表，走服务方法 |
| 追溯 / 看板 / OEE 查询 | `*QueryService` | READ_COMMITTED（`readOnly = true`） | 无锁读；查询超时 5s；走只读连接策略（OPT-008） |

**约定**：`@Transactional` 只加在 Service 公开方法上；事务内禁止远程调用与消息发送，异步一律先写 `outbox_event`；单事务 SQL 条数上限 20；死锁按业务键升序加锁预防，捕获 PostgreSQL `40P01` 后整体重试 1 次（04 §12.1、§12.4）。

### 6.2 并发控制

| 场景 | 策略 | 实现方式 | 失败处理 |
|------|------|----------|----------|
| 并发报工同一工单（RACE-001、AC-006） | 乐观锁 | `work_order.version` 条件更新；影响行数 0 即冲突 | 重试 1 次后返回 409 `VERSION_CONFLICT` |
| 报工与关闭并发（RACE-002、AC-008） | 状态前置校验 + 行锁 | 关闭事务内校验状态为 `PENDING_QC`；关闭后报工被状态机拒绝 | 409 `WORK_ORDER_STATE_INVALID` |
| 多工单同投一批次（RACE-004、BR-012） | 悲观锁 + 约束 | `SELECT ... FOR UPDATE` 锁批次行，再乐观锁扣减；`CHECK (qty_available >= 0)` 兜底 | 库存不足返回 400 `INSUFFICIENT_STOCK`，不产生负库存 |
| 同设备同时段排程（RACE-003、BR-004） | 排他约束 | GiST `excl_eq_slot` 拒绝第二条；服务预检提供可读冲突明细 | 409 `SCHEDULE_CONFLICT` + 冲突任务清单 |
| 重复点击下达 / 取消（RACE-005） | 状态前置校验 + 乐观锁 | 迁移表拒绝非法前置状态 | 409 `WORK_ORDER_STATE_INVALID` |
| 网关补传历史状态事件（RACE-006） | 事件时间戳判定 | 仅接受 `occurred_at > status_since` 的事件；旧事件只写历史表 | 不改变当前状态，返回 200 |
| 检验判定与处置审批并发（RACE-008） | 乐观锁 + 唯一索引 | `nonconformity.version` + `uk_do_nc_open` | 409 `DISPOSAL_ALREADY_OPEN` |
| 检验单录入与判定并发（FR-013 E3） | 乐观锁 | `inspection_order.version` 条件更新，判定为不可逆动作 | 409 `VERSION_CONFLICT` |
| 看板快照与实时更新竞争（RACE-007） | 版本化快照 | 快照带 `snapshotAt`，状态变更时延迟双删缓存键 | 前端展示数据时刻 + 延迟标记 |

### 6.4 最终一致性场景

| 场景 | 策略 | 补偿机制 |
|------|------|----------|
| 报满触发检验单生成（ST-006 → FR-012） | 事务性发件箱：报工事务内写 `outbox_event`，`OutboxWorker` 轮询投递（≤ 5s） | 重试 3 次后置 `FAILED` 并告警；`InspectionTimeoutJob` 每小时扫描未生成检验单的已报满工单并补建（BR-011 的 2 小时窗口从触发时刻起算） |
| 检验判定 → 下游工单 `BLOCKED`（ST-007） | 判定事务内更新检验单与不合格记录；工单状态由事件驱动同步 | 事件重放按 `aggregate_id + event_type` 幂等；看板高亮 + 对账任务比对 `nonconformity.status = OPEN` 与工单 `BLOCKED` |
| 设备看板快照（NFR-002） | `BoardSnapshotJob` 每 5s 聚合写 Redis，状态变更时延迟双删 | 快照带 `snapshotAt`；超 5s 未刷新由网关健康检查告警；降级为直查数据库（NFR-004） |
| OEE 与工作中心负荷（OPT-007） | `OeeAggregateJob` / `CapacityRecalcJob` 定时重算并覆盖写 `oee_daily` | 派生数据可全量重算；区间基础数据缺失返回 200 + `partial` 与缺失日期清单（AC-016） |
| 审计日志写入（NFR-006） | 异步批量（50 条或 200ms），失败重试 3 次 | 降级为同步写；按月对账审计条数与业务写操作条数，失败率 > 0.01% 触发告警（RSK-06） |
| 归档搬运（NFR-005） | `ArchiveJob` 年度执行，`INSERT ... SELECT` 分批搬运 | 搬运后行数对账；失败可从主表重跑；归档表保留只读访问路径 |

| 表 | 清理条件 | 物理删除时机 | 清理方式 |
|----|----------|--------------|----------|
| `idempotency_record` | `expire_at < now()` | 过期后立即删除 | 每日 1 次分批 `DELETE`（每批 5000 行）；非生产记录，不受保留期约束 |

### 7.3 冷热分离

- **触发条件**：`equipment_status_log` 单个分区超过 500 万行；或追溯查询 P95 超过 NFR-003 的 2s；或 `audit_log` 单分区超过 400 万行 / 2 GB。
- **路由策略**：以**时间分区裁剪**为主——查询携带时间范围时 PostgreSQL 自动裁剪分区，不扫描历史分区；追溯查询在 `timeRange` 缺省时默认取最近 365 天（FR-011 E3 的上限口径），避免全分区扫描；归档数据仅在显式携带时间范围且在线分区无结果时，由 `TraceService` 追加一次归档表 `UNION ALL` 查询，并在响应中置 `partial` 与数据来源标记。
- **不引入独立冷库**：首版单库 + 归档表空间已满足 3 年 600 万行的量级（06 §8 的归档数据量测算：首年 0、次年约 0.6 GB、3 年约 3.2 GB）；引入专用时序库或对象存储的收益低于运维成本（ADR-004 的备选方案对比）。

## 8. 查询优化建议

### 8.1 高频查询

| 查询 | SQL 示例 | 建议索引 | 预期性能 |

| 当日创建工单数（FR-001 E4 上限 200） | `SELECT count(*) FROM work_order WHERE created_at >= date_trunc('day', now()) AND is_deleted = 0` | `idx_wo_created (created_at DESC) WHERE is_deleted = 0` | < 20ms（仅扫当日索引段） |
| 排程甘特（按设备 + 日期区间） | `SELECT work_order_id, start_time, end_time, status FROM production_schedule WHERE equipment_id = ? AND start_time >= ? AND start_time < ? AND is_deleted = 0 ORDER BY start_time` | `idx_ps_eq_start (equipment_id, start_time)` | P95 ≤ 500ms（单次区间 ≤ 31 天） |
| 排程冲突预检（FR-005） | `SELECT work_order_id, start_time, end_time FROM production_schedule WHERE equipment_id = ? AND slot && tsrange(?, ?, '[)') AND is_deleted = 0 AND status <> 'CANCELLED'` | `excl_eq_slot`（GiST）+ `idx_ps_eq_start` | < 50ms（GiST 区间索引直接命中冲突） |
| 设备状态看板（FR-007） | 读 Redis 快照（TTL 5s）+ Caffeine 一级缓存；未命中时 `SELECT ... FROM equipment WHERE enabled = 1 ORDER BY equipment_code` | `uk_eq_code` | P95 ≤ 45ms（OPT-003 实测 640ms → 45ms） |
| 单设备状态历史 | `SELECT from_status, to_status, occurred_at FROM equipment_status_log WHERE equipment_id = ? AND occurred_at >= ? ORDER BY occurred_at DESC LIMIT 100` | `idx_esl_eq_time (equipment_id, occurred_at DESC)` + 分区裁剪 | P95 ≤ 420ms（OPT-006） |
| 离线设备扫描（每 10s，BR-006） | `SELECT id, equipment_code FROM equipment WHERE enabled = 1 AND current_status <> 'OFFLINE' AND last_report_at < now() - INTERVAL '60 second'` | `idx_eq_last_report (last_report_at) WHERE enabled = 1 AND current_status <> 'OFFLINE'` | < 20ms（200 台规模；部分索引远小于全表） |
| 告警升级扫描（每 60s，BR-007） | `SELECT id FROM equipment_alarm WHERE status = 'OPEN' AND level = 'P1' AND created_at < now() - INTERVAL '10 minute'` | `idx_ea_status_level (status, level, created_at)` | < 30ms |
| **正向追溯（FR-011，批次 → 工单）** | 递归 CTE 起点：`SELECT work_order_id, feed_quantity, feed_time FROM batch_feeding WHERE material_batch_no = ? AND feed_time >= ? AND feed_time < ?` | `idx_bf_batch (material_batch_no, work_order_id)` + `idx_bf_batch_time` | 单层 P95 ≤ 2s / P99 ≤ 5s（NFR-003）；建索引前 3 层实测 6.8s |
| **反向追溯（FR-011，工单 → 批次 → 上游工单）** | 递归 CTE 起点：`SELECT material_batch_no, feed_quantity, feed_time FROM batch_feeding WHERE work_order_id = ?`，随后按 `material_batch_no` 反向展开 | `idx_bf_wo (work_order_id)` + `idx_bf_batch (material_batch_no, work_order_id)` | 3 层链路 P95 ≤ 5s（OPT-004 实测 6.8s → 1.6s，结果集上限 1000、深度上限 3） |
| 追溯链路节点装配（批次 / 工单 / 检验结论） | 按上一步收集的批次号与工单号集合做批量 `IN (...)` 查询 | `uk_mbn`、`work_order` 主键、`idx_io_work_order` | 避免 N+1；装配阶段 < 100ms |
| 待检 / 合格批次列表（FR-009、FR-010） | `SELECT material_batch_no, material_code, qty_available, receive_time FROM material_batch WHERE status = ? AND is_deleted = 0 ORDER BY receive_time DESC LIMIT 20` | `idx_mbn_status (status, receive_time)` | P95 ≤ 500ms |
| BR-011 检验超期扫描（每小时） | `SELECT id, inspection_no FROM inspection_order WHERE status IN ('CREATED','INSPECTING') AND triggered_at < now() - INTERVAL '2 hour'` | `idx_io_status_triggered (status, triggered_at) WHERE status IN ('CREATED','INSPECTING')` | < 50ms |
| OEE 日查询（FR-008） | `SELECT availability, performance, quality, oee, partial FROM oee_daily WHERE equipment_id = ? AND stat_date BETWEEN ? AND ?` | `uk_oee_eq_date (equipment_id, stat_date)` | ≤ 60ms（OPT-007 实测 1.4s → 60ms） |
| 审计查询（按操作人 + 时间范围，FR-015） | `SELECT operator_id, action, target_type, target_id, occurred_at FROM audit_log WHERE operator_id = ? AND occurred_at >= ? AND occurred_at < ? ORDER BY occurred_at DESC LIMIT 20` | `idx_al_operator_time (operator_id, occurred_at DESC)` + 分区裁剪 | P95 ≤ 500ms |
| 审计查询（按对象） | `SELECT action, operator_id, occurred_at FROM audit_log WHERE target_type = ? AND target_id = ? ORDER BY occurred_at DESC LIMIT 20` | `idx_al_target (target_type, target_id, occurred_at DESC)` | P95 ≤ 500ms |
| 发件箱投递扫描 | `SELECT id, event_type, payload_json FROM outbox_event WHERE status IN ('PENDING','FAILED') AND (next_retry_at IS NULL OR next_retry_at <= now()) ORDER BY id LIMIT 100 FOR UPDATE SKIP LOCKED` | `idx_oe_status_retry (status, next_retry_at)` | < 20ms；`SKIP LOCKED` 支持多实例并行 |

**递归 CTE 裁剪约定**（FR-011、NFR-003）：递归项必须显式携带 `depth`（上限 3）、`visited`（环路检测数组）与时间范围条件，并在最外层加 `LIMIT 1000`；超限时置 `truncated = true`，断链节点置 `partial = true` 并返回断链清单（AC-022）。禁止在递归项中做无索引的字符串拼接或全量 `DISTINCT` 去重。

### 8.2 需避免的查询模式

- `SELECT *` — 应明确列出所需字段，避免带出 `remark`、`payload_json`、`before_summary` 等大字段，并保持覆盖索引可用。
- `ORDER BY rand()` 或无排序键的 `LIMIT` — 触发全分区扫描与排序；看板类查询必须带可索引的排序键。
- 循环中逐条查询（N+1）— 工单详情、追溯链路装配、告警列表一律使用 `IN (...)` 批量查询（OPT-002 将 42 条 SQL 降到 6 条）。
- 无时间范围的追溯查询 — 会跨全部历史分区扫描；`TraceService` 在 `timeRange` 缺省时强制取最近 365 天。
- 对分区表使用不带分区键的条件 — 例如仅按 `report_key` 查 `equipment_status_log`，将扫描所有年分区。
- 在 `batch_feeding` 上做无索引的模糊匹配（如前后通配的 `LIKE`）— 破坏正向追溯的索引命中；批次号检索一律前缀或等值。
- 对 `audit_log` 执行 `UPDATE` / `DELETE` — 权限层直接拒绝（9.3），应用层返回 403。
- 深分页 `LIMIT 100 OFFSET 100000` — 见 8.3。
- 事务内做全表 `count(*)` — 累计数量与看板统计走冗余列或预聚合表，不在写事务内聚合。

### 8.3 分页策略

- **浅分页（前 100 页）**：`LIMIT + OFFSET`，配合覆盖索引；`page` 从 1 起、`size` 默认 20、上限 100。
- **深分页（100 页之后）**：改用游标分页 `WHERE (planned_start_time, id) < (?, ?) ORDER BY planned_start_time DESC, id DESC LIMIT ?`；排序字段一律走白名单，禁止拼接未校验的列名。
- **总数保护**：`total` 超过 10 万行时以 `pg_class.reltuples` 估算并置 `totalIsEstimate = true`，前端提示收窄条件（OPT-009，深分页 P99 3.2s → 0.6s）。
- **追溯查询**：不使用 `OFFSET`，由结果集上限 1000 条与递归深度上限 3 层共同约束；超限返回 `truncated` 标记。
- **大数据量导出**：追溯报告与审计导出走异步任务 + 分批查询 + 文件流（Excel xlsx），导出行为写审计（`EXPORT_TRIGGERED`），不受分页限制但受时间区间（≤ 365 天）与行数上限约束。

## 9. 数据安全与合规

### 9.1 敏感字段

| 字段 | 敏感级别 | 存储策略 | 脱敏策略 |
|------|----------|----------|----------|
| `sys_user.password_hash` | 高 | BCrypt 哈希（cost ≥ 10），单向不可逆；禁止明文与可逆加密（NFR-007） | 任何接口与日志均不返回该字段 |
| `sys_user.username` | 中 | 明文；`lower(username)` 唯一索引防大小写重复 | 列表展示保留首位与末位字符 |
| `audit_log.source_ip`（INET） | 中 | 明文存储，仅内部留痕 | 对外导出按网段聚合展示，不逐条输出完整地址；文档与示例统一使用 RFC 5737 保留地址段（`192.0.2.0/24`） |
| `audit_log.before_summary` / `after_summary`（JSONB） | 中 | 字段值按 200 字符截断；**不写入**口令哈希、令牌、密钥等敏感值 | 查询与导出按 `target_type` 白名单字段渲染 |
| `material_batch.supplier_name` | 低 | 明文 | 列表展示不做脱敏，导出保留 |
| `outbox_event.payload_json`（JSONB） | 低 | 明文（业务字段快照，不含凭证） | 排障界面只读展示，不可编辑 |
| 数据库连接凭据 | 高 | 由环境变量 / 部署密钥注入，禁止写入代码仓库与迁移脚本（NFR-007）；配置示例使用 `change-me-on-deploy` 一类明文占位 | 日志中屏蔽连接串密码段 |

### 9.2 数据保留期限

- **生产记录与追溯记录**（`work_order`、`work_order_report`、`batch_feeding`、`inspection_order`、`inspection_item`、`nonconformity`、`disposal_order`）：≥ 3 年，保留期内不可物理删除（NFR-005）。
- **设备状态与停机记录**（`equipment_status_log`、`equipment_downtime`）：在线 1 年，总保留 ≥ 3 年；`OFFLINE` 时长仅保留原始记录，不参与 OEE 分母（BR-006）。
- **审计日志**（`audit_log`）：≥ 3 年，不可修改与删除（NFR-006）。
- **平台表**：`idempotency_record` 7 天、`outbox_event`（`DONE`）30 天，到期物理删除（非生产记录，不受保留期约束）。
- **备份数据**：应用发布前执行逻辑备份（`pg_dump -Fc`），保留 30 天；季度恢复演练一次（18 §12）。
- **归档数据**：`work_order_archive` / `work_order_report_archive` / 分离分区随主库一同备份，保留至总保留期届满。

### 9.3 审计日志

- **记录内容**：操作人（`operator_id`）、操作时间（`occurred_at`）、操作类型（`action`）、操作对象（`target_type` + `target_id`）、变更前后摘要（`before_summary` / `after_summary`）、操作来源（`source`）与来源地址（`source_ip`）——与 BR-015 的字段要求逐项对应。
- **覆盖范围**：工单状态变更、报工、投料、批次状态变更、检验判定、处置审批、权限变更 7 类关键写操作 100% 留痕（NFR-006）；排程人工调整（`SCHEDULE_ADJUSTED`）与导出（`EXPORT_TRIGGERED`）一并留痕（FR-006、FR-011）。纯查询操作不写审计日志，只记访问日志（BR-015 例外）。
- **记录方式**：应用层注解 + AOP（`AuditLogRecorder`）异步批量写入 `audit_log`；不采用数据库触发器（触发器无法获得应用侧的操作人与来源，且会放大写入延迟）。
- **不可篡改**：`meslite_app` 对 `audit_log` 仅授予 `INSERT` / `SELECT`，无 `UPDATE` / `DELETE` / `TRUNCATE`；应用层统一返回 `AUDIT_LOG_IMMUTABLE`（403，FR-015 E3）。**残余风险**：具备数据库超级用户权限的内部人员仍可直接改写历史行（15-安全评审 SEC-LOW-02），缓解措施为按日生成审计记录哈希链并在日切时校验前一日哈希，该加固为上线后跟进项。
- **查询与导出**：按操作人、操作类型、时间范围（≤ 365 天，FR-015 E4）查询；导出为 xlsx 并写 `EXPORT_TRIGGERED` 审计。
- **数据库账号权限划分**（15-安全评审 TB-3、18 §账号与权限）：

  | 账号 | 用途 | 权限 |
  |------|------|------|
  | `meslite_migrate` | Flyway 迁移 | 目标 schema 的 `CREATE` / `ALTER` / `DROP` / `COMMENT`，业务表 `SELECT` |
  | `meslite_app` | 应用运行 | 业务表 `SELECT` / `INSERT` / `UPDATE`；`audit_log` 与 `equipment_status_log` 仅 `INSERT` / `SELECT`；无 DDL、无 `DELETE`、无 `TRUNCATE` |
  | 备份账号 | `pg_dump` | 只读复制权限 |

## 10. 扩展策略

### 10.1 当前架构

- **数据库**：单实例 PostgreSQL 16 单主库，容器化部署，支持滚动升级（C-02）。
- **适用量级**：单表 < 1000 万行、读 QPS < 500、写 QPS < 200；首年全部表合计约 1450 万行 / 1.4 GB，容量余量充足（04 §5.2「分库分表不做」）。
- **已具备的扩展能力**：`equipment_status_log` 与 `audit_log` 的按年分区（可平滑增删分区）；部分索引与 BRIN 覆盖大分区；`outbox_event` 承载异步解耦；读写分离与缓存降级路径已在设计上预留（只读事务标记 `readOnly = true`）。

### 10.2 扩展触发条件

| 扩展动作 | 触发条件 | 预估时间窗口 |
|----------|----------|--------------|
| 增加年分区 / 归档表空间 | 次年分区缺失或单分区 > 500 万行 | 每年 1 次，滚动执行（已是常态动作） |
| 引入只读副本（读写分离） | 读 QPS > 1000，或主库 CPU 持续 > 70% | 6 个月内 |
| 引入 Redis 缓存层扩容 / 集群 | 热点数据 QPS > 2000，或看板快照命中率 < 0.9 | 3 个月内 |
| 提升连接池与只读连接策略 | 池等待峰值 > 0，或查询 P95 劣化 > 10% | 1 个月内（OPT-008 已给出 10 → 20 的取值） |
| 设备侧扩展至 200 台并缩短上报间隔 | 接入设备 > 200 台，或上报间隔 < 5s | 需复评分区与幂等策略（06 §9） |
| 分库分表 | 单表 > 1000 万行且写入 QPS > 200（`batch_feeding` 3 年约 300 万行，仍需 3 倍增长才会触及） | 12 个月内无计划 |
| 独立时序库 / 冷数据对象存储 | 归档分区 > 20 个，或归档数据量 > 3.2 GB 且在线查询仍频繁 | 归档表空间超过单机容量时评估 |

### 10.3 缓存策略建议（与 Performance Engineer 对齐）

- **缓存层次**：本地缓存（Caffeine）→ 分布式缓存（Redis）→ 数据库。
- **缓存模式**：以 Cache-Aside 为主；设备看板快照采用定时覆盖写（`BoardSnapshotJob` 每 5s）。
- **缓存对象与 TTL**（与 04 §13.4 一致）：

  | 对象 | 层级 | TTL | 失效方式 |
  |------|------|-----|----------|
  | 字典（报废原因、停机原因、单位） | Caffeine | 10min | 定时刷新 + 管理端手动失效 |
  | 设备看板快照 | Redis + Caffeine | 5s | 定时覆盖写 + 状态变更延迟双删 |
  | 设备台账与工作中心 | Caffeine | 5min | 台账变更主动失效 |
  | 工单详情热点（当日活跃工单） | Redis | 60s | 报工 / 状态变更时删除 |
  | 追溯查询结果 | Redis | 60s | 键含锚点与方向；投料或处置变更时删除相关键 |
  | OEE 日结果 | 数据库预聚合表 `oee_daily` | — | 定时重算覆盖 |

- **明确不缓存**：工单列表分页结果（条件组合多、命中率低）；批次可用库存 `qty_available`（BR-012 要求实时，必须读主库）；状态变更响应结果（幂等由 `version` 与唯一索引保证）。
- **一致性约束**：任何缓存都不得成为 `qty_available`、`work_order.status`、`inspection_order.status` 的判定依据；缓存读取失败必须回落数据库，不得使看板返回错误状态。
